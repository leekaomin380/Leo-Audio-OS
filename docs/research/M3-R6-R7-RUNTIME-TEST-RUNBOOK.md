## 1. 已闭合的离线事实（实验的理论基础）

从 MoKee 内核映像提取（`snd_kcontrol_new` → `soc_mixer_control` + TLV）：

```text
Volume: min=0 max=255 platform_max=255 reg=15 rreg=16 shift=0 rshift=0 invert=1
TLV   : SNDRV_CTL_TLVT_DB_SCALE, min = -127.50 dB, step = 0.50 dB
=> dB(v) = -127.50 + 0.50 * v      控件值越大越响
```

| 控件值 | 增益 | 含义 |
| ---: | ---: | --- |
| 205 | −25.0 dB | 当前值 / `mixer_paths.xml` 默认 |
| 213 | −21.0 dB | MIUI `hifi_volume = 0` |
| 225 | −15.0 dB | MIUI `hifi_volume = 30`（归档 logcat 值） |
| 229 | −13.0 dB | MIUI `hifi_volume = 40`（property manifest 值） |
| 253 | −1.0 dB | MIUI `hifi_volume = 100` |

R6 与 R7 的作用是**在实机上确认这套离线推导**，而不是去发现它。
如果实机结果与上表矛盾，**以实机为准并立即停止**，回到静态分析重做。

## 2. R6：Android 软件音量是否与 ES9018 `Volume` 叠加

### 2.1 目的

判定二者是**串联叠加**还是其中之一被旁路。这个结论决定：
（a）HiFi 音量上限如何设定；（b）R7 的主观对比是否只有一个变量。

**R6 必须先于 R7 执行。** 若跳过 R6，R7 的听感变化无法区分是 `Volume` 还是 Android 刻度造成的。

### 2.2 边界

* **只读 mixer，不写 mixer。**
* 只改变 Android 媒体音量（音量键或音量面板）。
* 不改变曲目、不改变耳机、不改变播放器、不改变 HiFi 路由状态。
* 不触碰账户、token、Apple Music 登录信息；截图前确认画面不含账户信息。

### 2.3 前置

1. 设备处于当前 MoKee 运行态，耳机已插入；
2. 使用**本地生成的固定测试音**（例如 M2 用过的 440 Hz / −20 dBFS / 44.1 kHz WAV），
   不使用流媒体，避免响度归一化干扰；
3. 播放已开始且稳定；
4. 记录起始状态：`Volume` 读回、当前 Android 媒体音量刻度、活动输出。

### 2.4 步骤

对 Android 媒体音量刻度 `0, 25%, 50%, 75%, 100%`（或该机实际的 0…15 分档中取 5 档）：

1. 用音量键把媒体音量调到目标刻度；
2. **只读**：采集下面的字段；
3. 记录一行数据。

### 2.5 采集字段（每档一行）

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `ts` | 主机时间 | — |
| `android_vol_index` | 音量面板 / `dumpsys audio` 的 STREAM_MUSIC 当前值 | 只读 |
| `volume_ctl_l`, `volume_ctl_r` | `tinymix` 读 `Volume` | **只读** |
| `quat_mm1` | `QUAT_MI2S_RX Audio Mixer MultiMedia1` | 确认路由未变 |
| `hphl_dac` | `HPHL DAC Switch` | 确认旁路未出现 |
| `slim_rx1_mux`, `slim_rx2_mux` | 两个 MUX | 同上 |
| `pcm_state` | `/proc/asound/card0/pcm0p/sub0/status` | 确认流仍 RUNNING |
| `subjective` | 用户口述 | "更响 / 更轻 / 无变化" |

### 2.6 判据

| 观察 | 结论 |
| --- | --- |
| 五档下 `volume_ctl_l/r` **恒为 205**，且主观响度随 Android 刻度单调变化 | **叠加成立**（Android 侧在软件混音器衰减，ES9018 侧独立）→ 推断 I-2 升格为事实 |
| `volume_ctl_*` 随 Android 刻度变化 | 存在未知写入者 → **立即停止**，重新审计谁在写该控件 |
| 主观响度不随 Android 刻度变化 | Android 音量未作用于当前路径 → **立即停止**，重新审计 |

### 2.7 停止条件

* 任一档出现 `hphl_dac != Off` 或任一 `SLIM RX MUX != ZERO` → 旁路出现，停止；
* `pcm_state` 不再 RUNNING → 停止；
* 出现任何异响 → 停止。

### 2.8 恢复状态

R6 **不改变任何 mixer 值**，因此恢复动作只有一条：
把 Android 媒体音量调回实验前记录的刻度。

## 3. R7：`Volume` 的方向、量级与安全边界

### 3.1 授权门（全部满足才可开始）

1. **项目主代理与设备所有者双方的明确、当场授权**；
2. R6 已完成且结论为"叠加成立"；
3. 设备所有者在场，耳机**不在耳上**（先外放确认或先离耳听），随时可以摘下；
4. 记录人和操作人可以随时中止。

### 3.2 边界（硬性）

* **人值守，逐步执行。不自动循环，不脚本化连续写入，不无人值守。**
* **不使用 229、253 或任何 > 225 的值。** 本轮上限是 225。
* 每一步：先写 → 立即读回 → 用户主观确认 → 才允许下一步。
* 任何异常立即写回 205。
* 结束时**无条件**写回 205 并读回确认。
* 不改变曲目、耳机、播放器与路由状态。
* 不触碰账户、token、登录信息。

### 3.3 前置

1. 确认 `Volume` 读回为 `205 205`；若不是，**停止**并先查清谁改了它；
2. **把 Android 媒体音量降到较低但仍可听的刻度**（建议 25–35%），并记录；
3. 确认 HiFi 路由仍成立（`quat_mm1 = On`，`hphl_dac = Off`，两个 `SLIM RX MUX = ZERO`）；
4. 固定测试音仍在播放且 `pcm_state = RUNNING`；
5. 记录起始主观响度描述。

### 3.4 阶段

| 阶段 | 目标值 | 预期增益 | 相对 205 | 进入条件 |
| --- | ---: | ---: | ---: | --- |
| A | **213** | −21.0 dB | **+4.0 dB** | 前置全满足 |
| B | **225** | −15.0 dB | **+10.0 dB** | A 完成、无异常、用户明确同意继续 |

**阶段 B 需要用户在听到 A 的结果之后再次口头同意。** A 通过不自动进入 B。

### 3.5 每步流程

```text
1. 写入目标值（左右声道同值）
2. 立即读回并记录 volume_ctl_l / volume_ctl_r
3. 若读回 != 目标值        -> 立即写回 205，读回确认，停止
4. 若左右不一致            -> 立即写回 205，读回确认，停止
5. 用户主观确认：响度是否升高？是否有失真、单边、爆音、静音？
6. 采集完整状态行（字段同 R6 §2.5，另加 target_value）
7. 停留不少于 10 秒再决定下一步
```

### 3.6 立即恢复 205 的触发条件

* 突发响度（比预期明显更响）；
* 任何失真、破音、削波感；
* 单边（左右不平衡）；
* 静音或断续；
* 读回值与写入值不一致；
* 左右读回不一致；
* 路由证据任一项变化（`quat_mm1` / `hphl_dac` / 两个 `SLIM RX MUX`）；
* 用户出于任何原因要求停止。

恢复动作：**写 205 → 读回确认 205 → 记录事件**。不重启（`boot` 为临时启动）。

### 3.7 判据

| 观察 | 结论 |
| --- | --- |
| 205 → 213 → 225 主观单调变响，读回精确命中，无失真 | 方向与量级与内核 TLV 一致 → G11 实机确认，I-3 升格为事实 |
| 单调变**轻** | invert 解读错误 → **停止**，`docs/19` §6 的整条映射曲线必须重算 |
| 读回不命中 | 存在第二写入者或控件语义不同 → 停止 |
| 225 时主观响度仍明显低于 MIUI 参照 | 存在第二个差异源（N-6）→ 记录残差，交由 A7 的 SPL 对照处理 |

### 3.8 结束

1. 写 205，读回确认为 `205 205`；
2. 把 Android 媒体音量恢复到 R7 前记录的刻度；
3. 记录结束状态行；
4. 归档：所有数据行 + 用户口述 + 任何异常事件。

**不得**把实验中用过的 213/225 留在控件里，也**不得**写入任何 property 使其在下次启动恢复。

| 观察 | 结果 |
| --- | --- |
| `Volume` 读回 | 五档全部为 `205 205`，**无变化** |
| QUAT 路由 | 稳定 |
| PCM | 稳定 |
| 主观响度 | 随 Android 刻度**单调变化** |

**判据命中 §2.6 第一行 → 叠加成立。**
推断 I-2 升格为事实：**Android 软件音量与 ES9018 `Volume` 是相互独立的串联增益。**
`Volume` 没有第二个写入者。

### 6.2 R7-A —— 通过

方法上的一处重要调整：**为避免 HAL 抢路由，先停止 Phonograph，改用同机原厂
64-bit `tinyplay` 直接打开 PCM0/MultiMedia1。** 这绕开了 AudioFlinger 的重路由，
也正是 F-19（`out_write: error -5` 周期性重路由）在本轮被发现的原因。

前置读回：前端 48 kHz / `S16_LE`；QUAT backend `S24_LE` / `KHZ_48`；
`HPHL DAC Off`；`SLIM RX1/RX2 ZERO`；`QUAT MM1 On`。

| 步骤 | 写入 | 读回 | 主观 |
| --- | ---: | ---: | --- |
| A | `205 → 213` | 精确命中，稳定 10 秒 | **明确变响**，无爆音 / 失真 / 单边 / 断续 |
| 恢复 | `→ 205` | 已确认 | — |

**结论**：控件方向与量级与内核 TLV 推导一致
（`dB = -127.50 + 0.50 × v`；205 = −25.0 dB，213 = −21.0 dB，差 **+4.0 dB**）。
`docs/19` F-4 / F-5 / F-6 在实机得到方向性确认。

### 6.3 R7-B —— **未执行**（2026-08-29 22:04 一次尝试，停在前置门）

目标值 `225`（−15.0 dB，相对 205 **+10.0 dB**）。

**不得记为通过。** 因此以下仍是推断而非事实：

* 「205 造成的 10.0–12.0 dB 缺口足以解释 MoKee 与 MIUI 的响度差」（`docs/19` I-3）；
* `docs/19` §6.2 中 `LEO_HIFI_CTL_CEIL = 237` 的最终取值。

执行 R7-B 时**仍须**满足 §3.1 的四项授权门，并逐条遵守 §3.5 / §3.6。

### 6.4 R7-A 附带产出：F-19

R7-A 的准备过程给出了一条本来不在计划内的关键实机事实：
在 AudioFlinger deep-buffer 流播放期间手工改 mixer，HAL 会每约 10.5–11.6 秒
返回 `out_write: error -5 - cannot write stream data: I/O error`，随后 standby 并
把路由改回 SLIMBUS/WCD，同时手工写下的 QUAT 仍可能保持 On。

这条证据的架构意义见 `docs/19` §1.5 与
`docs/research/M3-PATCH-AUTHOR-SELF-AUDIT.md` §2。

### 7.2 为什么停下

1. **路由未建立、无流在播。** 当前是完全空闲态：QUAT 与 SLIMBUS 都没有前端，所有 PCM closed。
2. **在这种状态下写 `225` 是无意义的**：`Volume` 只作用于 ES9018 支路，而 ESS 此刻既未上电

3. **本次任务的安全约束与 §3.3 的前置条件存在冲突，必须由用户裁决**：
   任务规定"除 ES9018 的 `Volume` 控件外，禁止修改其他 mixer 控件"，
   而建立 HiFi 路由需要写 `QUAT_MI2S_RX Audio Mixer MultiMedia1`（R7-A 当时就是这样做的）。
   **执行者不能自行放宽这条约束**，因此停下并上报。

### 7.4 恢复 R7-B 需要满足的条件（三选一）

| 方案 | 内容 | 谁来做 |
| --- | --- | --- |
| **A（推荐，沿用 R7-A）** | 用户或项目主代理用 `tinyplay` 直接打开 PCM0/MultiMedia1，并建立 QUAT 路由（写 `QUAT_MI2S_RX Audio Mixer MultiMedia1 = 1`，保持 `HPHL DAC Switch = Off`、`SLIM RX1/2 MUX = ZERO`），确认 `pcm_state = RUNNING` 后再交给执行者写 `Volume` | 需要**放宽**"只能改 Volume"的约束，或由用户手动完成路由 |
| B | 用户在设备上正常播放音乐（AudioFlinger 路径），执行者只写 `Volume` | ⚠️ **无效**：未打补丁的 HAL 会把路由送到 SLIMBUS/WCD，`Volume` 不在该支路上，写 225 依然没有可听效果 |
| C | 推迟 R7-B 到 M3-B 之后 | 届时打了补丁的 HAL 会自己选中 `hifi-headphones`，路由由 HAL 建立，执行者**只需**写 `Volume`，与"只改 Volume"的约束天然相容 |

**方案 C 在工程上最干净**：它同时消除了约束冲突和 F-19（播放中手工改 mixer 会被 HAL 撤销）
带来的不稳定性。代价是 `LEO_HIFI_CTL_CEIL` 的最终取值要等到 M3-B 之后才能定。

### 7.6 裁决（2026-08-29 22:0x，设备所有者）

**采用方案 C：R7-B 推迟到 M3-B 之后执行。**

理由（设备所有者确认）：打了补丁的 HAL 会自己选中 `hifi-headphones` 并建立路由，
执行者届时**只需要写 `Volume`**，与"只能改 Volume"的安全约束天然相容；
同时避开 F-19——播放中手工改 mixer 会被 HAL 每约 10.5–11.6 秒撤销一次。

由此产生的约束（写入合同）：

1. **不得**在 M3-B 完成之前重启 R7-B；
2. `LEO_HIFI_CTL_CEIL = 237` 在 R7-B 之前**保持为暂定值**，不得据此放宽上限；
3. `docs/19` M3-10 继续有效：213 / 225 / 229 中任何一个都不得成为产品默认，
   `platform_init()` 不写 `Volume`；
