# 02：工程学习与协作方式

Leo Audio OS 同时是一项产品工程和一条学习路线。它的近期目标是把 Xiaomi
Mi Note Pro（`leo`）构建为可靠的专用网络音频播放器；更长期的目标，是通过一台
真实、复杂、已有大量历史包袱的设备，建立设计自主硬件所需的系统能力。

未来理想硬件可能包含电子墨水屏与小型 LCD/LED 辅助屏、全键盘、短距离无线电、
低噪声音频链和高度克制的软件界面。Leo 不是该硬件的原型机，却是理解启动、驱动、
功耗、系统服务、产品边界和故障恢复的合适训练平台。

## 双轨交付

此后每个重要阶段同时产生两类结果：

1. **工程线**：源码、清单、脚本、镜像构建结果、测试记录、回滚材料和 Git 提交；
2. **教学线**：问题的背景、涉及的系统层、关键概念、为什么这样设计、替代方案、
   失败模式，以及这些知识如何迁移到未来的自研硬件。

只讲概念而没有可检查的产物，不算完成；只交付产物却无法解释其机理，也不符合本
项目的目标。

## 每个里程碑的讲解顺序

每项工作尽量按同一结构展开：

1. **问题**：当前要解决什么，为什么现在解决；
2. **层级**：它位于启动链、分区、内核、驱动、Android 系统、HAL、应用或硬件中的哪一层；
3. **证据**：查看哪些源码、日志、二进制依赖、测量结果或实机现象；
4. **设计**：采用什么方案，放弃哪些方案，权衡是什么；
5. **实现**：实际修改哪些文件或设备状态；
6. **验证**：用什么方法证明有效，并检查有无连锁退化；
7. **回滚**：失败时如何恢复到已知可用状态；
8. **迁移**：这次经验将来如何用于自研主板、显示、键盘、无线电或专用系统。

用户可以在任何一步提问。解释应优先依托正在处理的真实文件和设备现象，而不是脱离
工程讲一套抽象课程。

## 知识路线

### A. ROM 与启动链

- Boot ROM、Bootloader、分区表、boot/recovery/system/vendor 镜像；
- boot image、kernel、ramdisk、DTB/DTBO 的职责；
- Android Verified Boot、签名、启动失败和恢复路径；
- 为什么“删除一个应用”有时会让旧 MIUI 卡在启动标志。

### B. 内核、设备树与硬件控制

- Linux 内核配置、设备树、驱动 probe、时钟、电源域和 regulator；
- CPU 调频、热管理、睡眠状态和续航之间的关系；
- 显示、键盘矩阵、USB、I2C/SPI/UART、无线电和音频器件的接入方式；
- 如何区分硬件限制、驱动缺失和用户空间配置错误。

### C. Android 系统骨架

- init、属性系统、服务生命周期、Binder、权限和 SELinux；
- Framework、HAL、vendor blobs 与应用之间的边界；
- 组件依赖闭包，以及为何“看起来无关”的服务可能是启动必需项；
- 如何从通用消费系统收缩成单一用途产品，而不破坏可维护性。

### D. 音频链与可测量优化

- Spotify 到 AudioTrack、AudioFlinger、Audio HAL、DSP、I2S、DAC 和运放的完整路径；
- 重采样、混音、deep buffer、offload、时钟和功耗的关系；
- ESS9018K2M 相关专有组件的提取、依赖识别和兼容边界；
- 用日志、PCM 路由、温度、电流及音频测量建立证据，而不只凭听感下结论。

### E. 专用设备产品化

- 单一 HOME、播放器 Shell、隐藏维护模式和最小权限；
- Wi-Fi、VPN、更新、诊断和临时 ADB 的受控入口；
- 只读系统、可复现构建、SBOM、签名、OTA 和版本锁定；
- watchdog、启动计数、安全模式、自动回退和原厂恢复包。

### F. 向自主硬件迁移

- 先定义用途与失效模型，再选择 SoC、存储、显示和操作系统；
- 将电子墨水主界面与小型快速状态屏分工，避免用高刷新 UI 驱动所有交互；
- 将全键盘、短距离无线电和音频链作为一等硬件能力，而非后装外设；
- 从电源完整性、射频干扰、模拟/数字分区、散热和可维修性阶段就约束系统设计；
- 让维护界面与普通使用界面分离，使设备在日常状态下保持低干扰和确定性。

## `agy` 并行研究协议

本机已确认安装 `agy` CLI 1.1.15。用户授权在额度充足时使用 Gemini 3.1 Pro
等可用模型进行并行委派。它适合承担：

- 相互独立的公开资料检索与源码定位；
- 同一架构方案的不同立场评审；
- 依赖清单、测试矩阵和失败场景的交叉检查；
- 对补丁、文档或构建结果进行第二意见审计。

委派遵循以下约束：

1. 主工程线始终只有一个负责人；外部代理的输出是候选证据，不是最终事实；
2. 委派任务必须边界清楚、彼此独立，并说明所需输出格式；
3. 重要结论必须回到公开源码、官方材料、仓库文件或实机测试验证；
4. 每次有价值的委派记录实际模型、问题、结论、采用/拒绝理由和证据来源；
5. 不向外部代理发送签名私钥、账号、设备序列号、用户数据或不可公开的原厂文件；
6. 不让外部代理直接执行刷写、分区写入、删除或其他不可逆设备操作；
7. 并发用于增加证据覆盖面，不用来制造多份未经审查的答案。

如需保存评审，使用 `docs/reviews/YYYY-MM-DD-主题.md`。不必保存冗长原始对话，
但必须保留可复查的问题、证据和决策。

## 安全与权限

- 读取、解析、构建和离线验证可以持续推进；
- 刷机、格式化、分区写入、密钥替换等动作必须先明确目标、备份和回滚路径；
- 设备上的当前可用状态是基线，不因追求“更纯净”而轻易牺牲可启动性；
- 对尚未验证的推断明确标注，不把模型共识当作硬件事实；
- 每个可刷入产物都应能追溯到输入哈希、源码提交、构建步骤和验收结果。

## 第一课从哪里开始

项目的第一堂系统课不是编译一份庞大的 Android 源码，而是建立 **原厂音频依赖闭包**。
它会把 ROM 镜像结构、ELF 依赖、init 服务、权限、SELinux、HAL、内核接口和真实硬件
路径串在一起。完成后，我们不仅知道“该复制哪些音频文件”，还会知道每个组件为什么
存在、由谁启动、依赖谁、缺失时如何失败，以及它是否能被安全移植到第二代系统。
