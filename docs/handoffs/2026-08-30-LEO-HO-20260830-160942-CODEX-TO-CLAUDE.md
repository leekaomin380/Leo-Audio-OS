### J11 XML 表达、下发顺序及失败语义：部分有效，原稿须修正

已核验的源码行为：

- `audio_route.c` 的 ENUM 解析将字符串转换为控件枚举索引，kernel 暴露 QUAT BitWidth / SampleRate。**“现有 XML 未写控件”不能推出“XML 无法表达这些参数”。**
- `audio_route_update_mixer` 遍历 mixer 控件索引；`audio_route_update_path` 遍历 path setting，apply 正序、reset 逆序。真实目标 libaudioroute 的 Thumb wrapper 也对应路径更新，不能混用两条路径。
- 库调用硬件 setter 后未检查返回值，随后更新软件 old_value；这不足以保证真实写入成功。初始化有硬件读取，不能称完全无读取。
- 非法 ENUM 字符串记录错误并返回索引 0；名字和取值必须精确。

**拒绝直接采用 J11 的 XML 示例**：它写了 S16_LE / KHZ_96，违反本任务固定 48k/S24 的范围。不要安装、复制进候选或当默认配置。

原稿还错误地把所有重复 ctl 统一说成拒绝：直接 `<ctl>` 经 `path_add_value` 可复用并更新同一 setting；嵌套 path 经 `path_add_setting` 的重复检查是另一条路径。冷启动“乱码”、必然竞态、几百毫秒 Watchdog 等推断无证据，全部不采纳。真实行为需精确引用函数，不沿用修辞。

### J13 usecase 可达性：原稿整体不通过，不能据此改代码

**严重错误**：把 device alias 当作 backend suffix，宣称必须补 `... headphones` 路径、必须新增 C 枚举。实际 `platform_add_backend_name` 只读取 `backend_tag_table`；原版普通 headphones 后缀为空，alias 不参与后缀拼接。该任务上下文缺了 setter 和宏定义等片段，但缺材料应标未知，不能编造。

Codex 已独立确认且可保留的部分：

- `get_offload_usecase`：multi_offload_enable=false 时，is_compress=true 选 OFFLOAD2，false 选 OFFLOAD；true 时从共享位图池找空位。实际属性值仍未知；源码 `audio_hw.c:4103` 的读取默认值为 false。
- 归档缺少 `compress-offload-playback2 hifi-headphones`，因此两节点 XML 路线存在**可达条件明确的覆盖缺口**。不能断言 Spotify/Apple Music 实际使用此分支。
- PRIMARY 是宏别名，不是猜测的 primary-playback：`audio_hw.c:87–93` 按 USE_LL_AS_PRIMARY_OUTPUT 选择 low-latency 或 deep-buffer。
- 普通 DIRECT flag 不等于 DIRECT_PCM；不要沿用原稿对应用或 flag 的猜测。
- enable_audio_route 忽略路径 apply 返回值，不等于系统绝不会产生后续 AudioTrack/PCM 错误。

独立映射：第二批 **`Codex独立核验-前端路由映射.json`**。现有四条 HiFi 路径分别是：deep-buffer→MM1、low-latency→MM5、ULL→MM3、首个 offload→MM4；offload2 的无后缀基础路径用 MM7。**原 P0 报告把四条都说成 MM1 是错误的。**

### J14 QUAT 生命周期：源码事实可用，架构与 ACDB 推断不采纳

Codex 已核验：

- 固定 kernel 的 `msm8994.c:245/247` 静态默认值为 48k/S24_LE。
- QUAT fixup 在 `2229` 附近使用 sample_rate 变量，FORMAT 硬编码 S24_LE，未用 bit_format 变量设置 FORMAT；没有在此处设置通道数。
- startup 的 MASTER 分支根据 bit_format/rate 选时钟；SLAVE 分支设置 external clock。实际编译模式及当前设备状态不能从片段默认。
- `platform_set_codec_backend_cfg` 的两个控件硬编码为 **SLIM_0_RX Format / SLIM_0_RX SampleRate**，不是 QUAT；更改 hw_interface_table 不会自动改这两个字符串。
- alias/backend 两项本身不改 ACDB ID 10；但 ACDB 并非永远不能由 XML 覆盖，存在单独的 acdb_ids/setter 机制。正确 ID 及实际影响未知。

**拒绝**原稿的“默认行为可以通关”“不加 C 当前也不会死机”“ID 10 极为有害／第一怀疑对象必须是 ACDB”“必须反编译 ACDB”等结论。它把条件分析升级为架构裁决，违反任务边界。FE S16 与 BE S24 也不能直接判成冲突或无冲突；DSP 行为仍需证据。
